# Reviewed development team

For a new implementation request from chat, use [APEX work from chat](../apexrest-work/SKILL.md). It honors the saved execution mode, opens its panel inside Codex and returns the result to the originating chat without requiring a web form. The low-level team API below remains available for explicit orchestration.

For an implementation task, call `apexrest_team_start` with the user's absolute configured application `project` and their complete task, constraints and existing authorization. Omit options to use saved preferences. `executionMode: single` creates exactly one session for planning, implementation and self-verification; `team` creates separate manager, developer and QA sessions. The default is `single`. Team is allowed only after the user explicitly enables `multiAgentEnabled` in Settings. Launch overrides cannot enable it. Never change the setting without the user's explicit request. Do not replace this with optional model-chosen subagents or perform the implementation in the host conversation. Source edits default to a project write sandbox; select `read-only` for analysis-only tasks. In team mode, `developers` selects one to three developer sessions; single mode always uses one regardless of the stored developer count. The runtime serializes their edits to avoid collisions.

In team mode, the state machine runs planning, development, manager code review, independent QA, and manager review of QA. A request for repairs returns to development and repeats both reviews, with at most three revisions. The host cannot mark a team complete or supply its own approvals. Only `status: completed` in team mode is a reviewed result, and its source digest must still match. `review_stale`, `review_failed`, `blocked`, `outcome_unknown` and `cancelled` are not successful completion. Single mode instead records `verification` checks from the same agent, completes only when all required checks pass, and reports `result_stale` if files later change. It has no manager or independent QA. Reports are agent evidence, not proof that an unavailable Oracle/browser check ran.

Use `apexrest_team_wait` with the previous cursor and `waitSeconds: 25`; unchanged replies omit repeated histories. Read full `apexrest_team_status` only when details are needed and summarize concrete changes in phase or findings. Use `apexrest_team_message` for user corrections while the team is active; status distinguishes queued and acknowledged messages. New user input invalidates earlier completion decisions. Use `apexrest_team_cancel` when the user stops the work. Cancellation does not revert file or database changes. Never retry an unknown outcome automatically.

The team owns its App Server process and sessions. It does not attach to the user's current desktop conversation. In team mode, its members share only this project's files, a scoped roster, peer reports and messages through `team_context` and `team_message`. The plugin supplies these tools; no public API for the desktop's private subagent bus is assumed. Members cannot spawn additional agents or managers. Manager and QA use read-only sandboxes and read-only APEXREST tools, plus the scoped verification-browser opener. Background sessions cannot approve escalations or provide missing interactive credentials.

If `apexrest.json` is absent, use the project workflow to initialize or adopt the requested project before starting. Project trust and Codex login must already be valid; report the exact setup blocker without changing host trust or copying tokens. This skill does not authorize downloads, publication, environment provisioning or database changes. For identified authorized application imports, preserve the existing plan/apply, target, backup and runtime-verification requirements. Administrative setup, reference lookup and connection diagnostics remain individual tools; they do not produce a reviewed application implementation.

Use `$apexrest-panel` to follow the team in Codex. Stable plugin agent names and panel avatars are Mewtwo (manager), Pikachu, Charmander and Bulbasaur (developers), and Squirtle (QA). These identities do not change review gates, sandboxes or peer routing keys.

Both modes retain the dashboard, observed activity, tokens, user steering and cancellation. `browserMode` selects `codex` or `external` for interactive APEX verification; it is pinned at launch. Follow the [selected-browser rule](../apexrest-test/SKILL.md#in-app-browser-verification). The dashboard itself stays in Codex.
