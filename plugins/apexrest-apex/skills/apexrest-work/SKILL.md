# APEX work from chat

Use this workflow for Oracle APEX implementation requests in the current host chat. Existing worker sessions continue their assigned role and must not start another run. Preserve the complete task, constraints, acceptance criteria and existing authorization. The user does not need to re-enter the task in the dashboard.

1. Resolve the absolute application project containing `apexrest.json`. Initialize/adopt it through the project workflow when necessary. Do not silently select another project, grant trust or expand database permissions.
2. Generate a fresh UUID `requestId` and call `apexrest_work_start` with `project` and `task`. Omit execution/browser/developer/sandbox/timeout options to honor saved project settings. Explicit user choices may override `executionMode: team|single` and `browserMode: codex|external` for this request. The default without saved settings is team with the Codex in-app verification browser. Models and reasoning are Auto. The returned `teamId` identifies a private run in either mode, not a new user-owned chat.
3. Open the exact returned `panel.url` with `open_in_codex` or available Codex in-app browser controls in this chat. The dashboard stays inside Codex even when APEX verification uses an external browser. Keep the capability URL private. In CLI, use `apexrest panel tui --project PATH` in an interactive terminal, or follow progress in this chat. A URL alone does not establish rendering.
4. Keep the request active. Use `apexrest_team_wait` with `id`, the returned `cursor` and `waitSeconds: 25` until `terminal: true`. Report meaningful changes and limitations. Forward corrections with `apexrest_team_message`; stop with `apexrest_team_cancel`. Do not end the turn merely because work was queued.
5. Deliver changes, observed checks and limitations in this same chat. Inspect the recorded `executionMode`. In `single`, one owned session plans, implements and verifies; report its `verification` checks as self-verification. Do not invent a manager approval or independent QA. In `team`, require both manager reviews and independent QA. Only `completed` with a current source digest is completed work. `result_stale`, `review_stale`, `verification_failed`, `review_failed`, `blocked`, `cancelled` and `outcome_unknown` are not success.

Settings are in the panel under execution mode and APEX verification browser, and apply to new runs from chat, CLI and panel. Active runs retain their selected modes. Single mode retains live actions, model/token usage, messages, cancellation, diagnostics and source-bound results. It never creates reviewer sessions or delegates work. Team mode retains the enforced developer → manager code review → independent QA → manager QA review cycle. Both remain subject to project trust, sandbox and deployment authorization.

Follow the [browser verification rule](../apexrest-test/SKILL.md#in-app-browser-verification) using the run's `browserMode`. Use `apexrest_browser_open` for the explicit environment: `codex` returns a URL to open through host in-app controls; `external` launches the system browser for interactive login/SSO. Browser control and actual verification are separate from opening a URL. Background sessions may lack the selected browser controls; record this limitation instead of substituting a different browser or claiming a pass.

For an uncertain start, inspect the original `requestId` with `apexrest_team_status`. Exact retries reuse the run and its original settings even after defaults change. Changed inputs require a new ID. If the panel fails, retain the run ID and continue monitoring. If the host has an old catalog, use the installed CLI equivalents with the same arguments. The plugin does not intercept every message globally or deliver callbacks into closed chats; recover interrupted work by its ID.

Reference, setup and connection diagnostics remain individual tools. An authorized identified application import still requires the deploy workflow, target checks, backup and runtime verification; completion alone is not a deploy grant. No publication, external messages, dependency installation or broader database authorization is implied.
