# APEX work from chat

Use this workflow for an Oracle APEX implementation request in the current host chat. Existing team member sessions continue their assigned role and must not start another workflow. The user describes the desired result; Codex handles task creation, panel display and completion reporting. Do not ask the user to enter the request again in the panel. For a reference question or connection/setup diagnosis, use the individual tool instead of starting an implementation team.

1. Resolve the user's configured application directory containing `apexrest.json` from the current project and conversation. If it needs initialization/adoption, use the project workflow first. Preserve the complete task, constraints, acceptance criteria and existing authorization. Do not silently select another project, grant trust or expand database permissions.
2. Generate a fresh UUID `requestId` and call `apexrest_work_start` with the absolute `project` and complete `task`. One developer is the default; add developers only for useful distinct assignments. Models and reasoning are Auto, without manual configuration. Use `sandbox: read-only` for an explicitly requested analysis-only team. The returned `teamId` is an internal reviewed run, not a new user-owned Codex chat.
3. In Codex desktop, open the exact returned `panel.url` with `open_in_codex`, or the available Codex in-app browser tool, in this same chat. It selects the new team automatically. Do not open an external browser or ask the user to click Start. Keep the local capability URL private. In Codex CLI, use `apexrest panel tui --project PATH` in an available interactive terminal; if there is no separate interactive surface, follow progress in the current chat. A URL alone does not establish that the panel rendered.
4. Keep this request active. Call `apexrest_team_wait` with `id: teamId`, the returned `cursor` and `waitSeconds: 25`. Repeat with each new cursor until `terminal: true`. Report meaningful phase changes or blockers without dumping tool logs. Do not end the response merely because a team was queued. The wait tool avoids heartbeat polling; its timeout is not task failure. Forward user corrections with `apexrest_team_message`; use `apexrest_team_cancel` when the user stops the work.
5. Deliver the terminal result in the originating chat: what changed, the manager's two review decisions, QA's observed checks, and remaining limitations. Only `team.status: completed` with a current source digest is a reviewed result. `review_stale`, `review_failed`, `blocked`, `cancelled` and `outcome_unknown` require their actual findings; none means success. Follow the existing deploy skill when the user's request also authorizes an identified application import. Team approval alone is not a deploy grant.

For an uncertain start, inspect `apexrest_team_status` using the original `requestId` (also the team ID). An exact retry of `apexrest_work_start` with the same UUID and unchanged inputs reuses the run; a changed task requires a different request. Never create a replacement merely because display failed or delivery is uncertain. If the panel is unavailable, retain the team ID, continue monitoring and report the display limitation. If the current host has cached an older tool catalog, use the installed CLI equivalents `apexrest work start` and `apexrest team wait` with the same arguments; do not bypass the team in the host conversation.

The plugin enforces the developer → manager code review → independent QA → manager QA review sequence in separate owned Codex sessions. The skill keeps the host chat responsible for opening the panel and presenting the result. It does not install a global message interceptor or inject a callback into an unrelated chat. If the host turn is interrupted or closed, recover by the same team ID and continue monitoring. No automatic new user chat, external message, publication, dependency installation or broader database authorization is implied.
