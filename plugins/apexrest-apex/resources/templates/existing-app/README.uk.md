# Перенесення наявного застосунку

[English](README.md) | Українська

Створіть каркас проєкту `existing-app`, налаштуйте точну наявну тестову ціль та іменоване з’єднання для читання, потім виконайте `project adopt --env dev --app-id ID`. Експорт відбувається через приватний проміжний каталог, а встановлення — лише в новий каталог коду. Якщо він уже існує, перенесення завершується з LOCAL_EDITS_CONFLICT; локальні зміни зберігаються. Для наступних експортів використовуйте новий каталог `apex export --env dev --output review/export-UUID`.

Зберігайте `.apex`, Oracle ID, спільні LOV, автентифікацію та всі файли сторінок під контролем версій. `apex diff --env dev` порівнює хеші файлів коду зі свіжим експортом Oracle. Це текстовий перелік, а не доказ повного семантичного покриття компонентів. Експорти SQLcl використовують початкові ID та опускають часові мітки експорту; жодна вигадана нормалізація не видаляє метадані.

Інтеграційний запуск для випуску має експортувати до й після повного імпорту без змін і порівняти кожен файл/компонент, потім змінити одну сторінку й перевірити працездатність іншої сторінки та спільного LOV. Поточний локальний запуск не має дозволеної бази даних і не може засвідчити ці сценарії. Непідтримувані компоненти мають завершувати валідацію/експорт із корисною помилкою; ніколи не пропускайте їх непомітно й не редагуйте внутрішніх таблиць APEX вручну.
