# Каталог патернів

[English](pattern-catalog.md) | Українська

Знайдіть готову UX-композицію Oracle APEX і адаптуйте її рецепт APEXlang до свого застосунку. Каталог патернів відокремлений від [каталогу компонентів](component-catalog.uk.md): компоненти описують окремі елементи, а патерни зберігають компонування, потік даних і взаємодію між ними. Обидва каталоги є локальними ресурсами, з якими агент працює через наявні довідкові інструменти. Для пошуку патернів не потрібні з’єднання з БД, інтерфейс каталогу або автоматичне вставлення.

Цей каталог і skill його наповнення підготовлено для `apexrest@1.2.0`. Публікацію дозволено; підтвердження в реєстрі ще очікується. [Запис публікації 1.1.0](evidence/npm-110-publication.json) описує попередній випуск каталогу компонентів. Оновлення кешу встановленого плагіна залишається окремою дією.

## Пошук і використання

```sh
apexrest docs search --corpus patterns --query "search" --kind template --version 26.1 --limit 3 --json
```

Еквівалентний виклик MCP — `apexrest_reference_search`:

```json
{
  "corpus": "patterns",
  "query": "search",
  "kind": "template",
  "version": "26.1",
  "limit": 3
}
```

Читайте отриманий ID `pattern:` через `apexrest_reference_read` або `apexrest docs read --id ID --json`. Поле `nextOffset` дає потрібне продовження документа, а `nextResultOffset` — наступні результати пошуку. Англійські та українські пошукові назви ведуть до тих самих записів. Типовим корпусом залишається `apexlang`; значення ID `component:` і наявних посилань Oracle не змінюється.

Перед вибором рецепта перевірте джерела поточного проєкту, версію APEX, тему та MMD. Прочитайте контракт даних і потрібні посилання `component:`/`oracle:`. Узгоджено адаптуйте номери сторінок і назви елементів, DOM ID, ключі, проєкції SQL, submitted items, дії та shared references. Додайте композицію до наявного застосунку без копіювання автентифікації чи конфігурації застосунку-джерела. Скомпілюйте адаптований застосунок і використайте наявний процес дозволеного розгортання та браузерної перевірки.

Читайте покриття через `pattern:source/<sourceId>/review`, а рішення щодо сторінки — через `pattern:source/<sourceId>/review/page-<id>`. Щоб знайти ці записи, шукайте в корпусі `patterns` із `family: "coverage"`. Покриття означає огляд усіх спостережених сторінок і змістовних варіантів; воно не означає окремий рецепт для кожної можливої комбінації опцій шаблону.

## Джерела й докази

Каталог охоплює два джерела на APEX 26.1.4 та Universal Theme 26.1: [Universal Theme Reference](https://apex.oracle.com/ut), що має 122 сторінки, та Oracle APEX UX Pattern Catalog із 28 сторінками. Кожна захоплена сторінка має явний огляд структурних і поведінкових варіантів. Окремі компоненти, візуальні опції, документація, неактивні елементи керування й порожні концепції відокремлені від готових композицій. Публічні записи містять безпечне зазначення джерела, сумісність і хеші вмісту. Необроблені експорти й приватні дані цілі залишаються поза пакетом. Право на поширення не підтверджене; каталог використовує фактичні метадані та власні рецепти без копіювання текстів, JavaScript чи ресурсів джерел.

[Локальний manifest](../resources/patterns/manifest.json) фіксує 150 перевірених сторінок, 818 рішень щодо варіантів, 58 контрактів патернів і 84 рецепти. Шістдесят дев’ять рецептів містять власну реалізацію; 15 залишаються явно невирішеними варіантами чи концепціями. Усі 69 реалізованих рецептів мають докази реальної офлайн-компіляції SQLcl без попереджень; зведена перевірка додає 56 реалізацій до 13 наявних підтверджень. Ці кількості описують підготовлений bundle 1.2.0; публікація й перевірки чистого встановлення фіксуються окремо.

Розширений інвентар не означає змін у застосунках-джерелах. Digest UX-експорту збігається з попереднім захопленням, а всі 147 раніше захоплених файлів джерел Universal Theme зберігають свої хеші. Нове захоплення також інвентаризує 53 binary/static resources як факти без їхнього поширення. Reader тепер зберігає анонімні декларації, ключі в лапках і повторювані ключі в контексті декларації: UX-джерело має 1099 об’єктів, зокрема 102 shared components і 15 раніше пропущених анонімних декларацій; для Universal Theme збережено всі сім анонімних branches.

Рецепт зі статусом `ready` має повний задекларований набір локальних залежностей і докази реальної офлайн-компіляції з його каркасом та MMD. Перевірка джерела, компіляція, виконання SQL, імпорт і браузерна перевірка — окремі результати. `not-run` не означає успішну перевірку. Непідтримана поведінка й невизначені залежності залишаються явними. Синтетичні приклади визначають форму вхідних даних, а не бізнес-схему користувача чи гарантію поведінки після запуску.

Перевірені джерела та власні рецепти мають конкретні обмеження:

- Форми UX-джерела демонструють структуру без налаштованого DML бізнес-даних. Власні рецепти форм можуть декларувати окремий SQL-скрипт fixture; його виконання потребує дозволеної цілі та не входить до офлайн-компіляції.
- Приклад AI в UX-джерелі не має налаштованого провайдера. Каталог не заявляє робочу AI-інтеграцію й не створює облікових даних.
- Рецепти списку й дерева явно розрізняють native переходи між сторінками та власні варіанти вибору й оновлення. JavaScript застосунків-джерел не копіюється; кожен рецепт визначає підтриману взаємодію.
- Порожні концепції master-detail залишаються unresolved до появи повної композиції та її доказів.
- Посилання-заглушки `#`, назви дій без обробників, застарілі mobile-приклади й специфічні розширення застосунків не стають робочими рецептами після компіляції. Їхні обмеження й unresolved-варіанти залишаються видимими в оглядах сторінок.

## Додавання патернів з іншого застосунку

Викличте `$apexrest-pattern-catalog`, щоб додати або оновити записи каталогу з визначеного застосунку APEX. Цей skill призначений для наповнення каталогу; звичайне використання наявного патерна виконується через `$apexrest-apexlang`.

Інструменти захоплення й побудови для супроводжувача запускаються з [репозиторію джерел APEXREST](https://github.com/apexrest-dev/apexrest-codex). Установлений плагін може шукати наявні патерни без цього checkout. Не редагуйте кеш установленого плагіна й не припускайте, що скрипти репозиторію постачаються поруч із його skills.

Задайте `PATTERN_CONNECTION`, `PATTERN_APPLICATION_ID`, `PATTERN_WORKSPACE` і `PATTERN_SCHEMA` для дозволеного джерела, доступного лише для читання. Задайте `PATTERN_SOURCE_ID` як сталий slug без приватних даних; він обов’язковий в обох режимах захоплення. Збережіть snapshot у новому приватному каталозі:

```sh
node scripts/capture-pattern-snapshot.mjs --connection "$PATTERN_CONNECTION" --application "$PATTERN_APPLICATION_ID" --workspace "$PATTERN_WORKSPACE" --schema "$PATTERN_SCHEMA" --source-id "$PATTERN_SOURCE_ID" --compiler /path/to/sqlcl/lib/apexlang-compiler.jar --output /tmp/apexrest-pattern-snapshot-new
```

Захоплення перевіряє фактичну ідентичність цілі перед читанням метаданих і експортом джерел. Воно не імпортує застосунок і не змінює бізнес-таблиці. Перегляньте приватний snapshot, виберіть композиції, замініть специфічні деталі застосунку й підтвердьте право на поширення. Сам доступ до застосунку-джерела не надає права поширювати його код.

Використовуйте сталий ID джерела під час оновлень. Нові застосунки додають окремі джерела; однакові назви сторінок не повинні перезаписувати патерни іншого джерела. Перед злиттям перевіряйте зміни джерела, видалені записи, конфлікти ID і зміни сумісності. Зберігайте наявні ID, якщо їхнє значення не змінилося. Необроблені snapshots залишайте приватними; до публічного набору включайте лише перевірені метадані, власні або дозволені до поширення рецепти й безпечне зазначення джерел.

Нормалізуйте перевірений snapshot із тим самим ID джерела:

```sh
node scripts/capture-pattern-snapshot.mjs --snapshot /tmp/apexrest-pattern-snapshot-new --publish resources/patterns/source --source-id "$PATTERN_SOURCE_ID"
```

Нормалізація записує `source/<sourceId>/snapshot.json` та `inventory.json`. Наявні ID джерел відхиляються, якщо не задано `--replace` для перевіреного оновлення того самого джерела. Перед перевіркою підготуйте патерни й рецепти в `resources/patterns/recipes/registry.json`, зберігаючи зв’язки з джерелом і записи інших джерел. Додаючи записи, звіртеся з поточною схемою builder. Verifier також приймає `--changed`, `--filter=REGEX` і `--catalog=DIR`; builder приймає необов’язковий каталог як аргумент.

Зберігайте захоплені факти незмінними. Використовуйте необов’язкову registry map `sourceClassifications`, щоб класифікувати нові або перекласифіковані сторінки як `pattern`, `group`, `primitives`, `documentation`, `scaffolding` чи `placeholder`. Також додайте обов’язкові записи `sourceReviews` для кожної сторінки кожного джерела, де ключами є ID джерела та ID сторінки як рядок. Наприклад, цей фрагмент описує одну перевірену сторінку:

```json
{
  "sourceClassifications": {
    "example-source": { "10": "pattern" }
  },
  "sourceReviews": {
    "example-source": {
      "10": {
        "sourceSha256": "<copy inventory page provenance.sha256>",
        "classification": "pattern",
        "patternIds": ["pattern:example/review"],
        "componentIds": ["component:regions/standard"],
        "reason": "A reviewed composition connects the listed regions and actions.",
        "variants": [
          {
            "name": "Primary interaction",
            "disposition": "pattern",
            "patternIds": ["pattern:example/review"],
            "reason": "The included recipe implements the observed interaction."
          }
        ]
      }
    }
  }
}
```

Замініть ілюстративні digest та ID фактичними значеннями інвентаря й каталогу та перевірте всі інші сторінки. `sourceSha256` має дорівнювати точному `provenance.sha256` цієї сторінки. Дозволені disposition для варіантів: `pattern`, `component`, `visual`, `documentation` і `unresolved`. Інвентаризуйте вкладені декларації, анонімні branches, ключі в лапках, повторювані ключі з батьківським контекстом, shared dependencies та кожну змістовну дію чи стан. Назва кнопки, посилання `#` або назва шаблону самі собою не доводять робочу поведінку. Записуйте фактичні приклади джерела з ID сторінок і точними ключами компонентів з інвентаря; явно фіксуйте непідтриману поведінку.

Builder відхиляє відсутні чи застарілі огляди, невідомі сторінки або source anchors, некласифіковані сторінки та патерни, не згадані в оглядах їхніх сторінок-джерел. Кожна сторінка з класифікацією `pattern` потребує посилання на патерн. Placeholder не є робочим рецептом. Після підготовки виконайте:

```sh
node scripts/verify-pattern-recipes.mjs
node scripts/build-pattern-catalog.mjs
node scripts/build-pattern-catalog.mjs --check
```

Перевірте кожен рецепт зі статусом ready, перебудуйте каталог і підтвердьте відтворюваність результату, залежності, хеші доказів, обмежений обсяг відповідей і роботу встановленого пакета поза репозиторієм. Вибіркова перевірка не скасовує вимог до доказів для інших готових рецептів. Синхронно оновлюйте англійську й українську документацію. Наповнення каталогу не публікує реліз і не дозволяє імпорт застосунку.

Поточні докази й залишок роботи наведено у [стані реалізації](implementation-status.uk.md), [матриці приймання](acceptance.json) та [наступних діях](next-actions.uk.md).
