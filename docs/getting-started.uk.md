# Початок роботи

[English](getting-started.md) | Українська

Встановіть нативний плагін Codex, перевірте його локальне середовище виконання, потім налаштуйте явну ціль Oracle. Репозиторій містить середовище виконання плагіна: для нативного встановлення не потрібно збирати TypeScript або запускати `npm ci`.

Поточна версія є бета-випуском. Докази роботи нативного хоста стосуються перевіреного поєднання Codex і платформи; [умови стабільного випуску](next-actions.uk.md) залишаються відкритими.

## Передумови

| Вимога | Коли потрібна |
| --- | --- |
| Codex із підтримкою нативних плагінів | Реєстрація плагіна; Codex CLI 0.154.0 перевірено на macOS arm64 |
| Node 24 LTS у `PATH` | Запуск зібраного MCP середовища плагіна з репозиторію |
| Java 21 і перевірений SQLcl 26.1.2 | Генерація, валідація, експорт та імпорт Oracle |
| Наявна підтримувана ціль Oracle APEX | Для сценаріїв із підключенням потрібен APEX 26.1+ |
| Іменовані з’єднання SQLcl | Дозволений доступ до налаштованої цілі, збережений локально |
| Chromium і відповідні тестові залежності | Браузерні/API набори; utPLSQL — лише коли його потребує SQL-набір |

Для звичайного розгортання достатньо наявної чистої інсталяції APEX. Службові таблиці, utPLSQL та розгорнута пісочниця не є загальними передумовами імпорту лише застосунку. Встановлення з коду не включає бінарні файли Oracle, браузерні облікові дані чи обліковий запис бази даних.

## Встановлення плагіна

У терміналі, де доступні Node 24 і Codex CLI:

```sh
node --version
codex --version
codex plugin marketplace add apexrest-dev/apexrest-codex
codex plugin add apexrest-apex@apexrest
codex plugin list --json
```

Нативне встановлення перевірено з Codex 0.154.0, Node 24.21.0 та macOS arm64; [звіт нативного встановлення](evidence/native-repository.json) фіксує точне джерело й обсяг перевірки.

Це реєструє marketplace `apexrest` із репозиторію та його плагін `apexrest-apex` у вибраному профілі Codex. Після встановлення почніть нову задачу Codex і надайте запит:

> Скористайся APEXREST, щоб перевірити моє налаштування. Виклич doctor плагіна й окремо оціни доступність нативних інструментів, готовність компілятора та підключення до бази даних. Допоможи завершити відсутні локальні налаштування, не запитуючи паролів у чаті.

Перевірте фактичний результат `apexrest_doctor`. Успішна реєстрація чи запис у списку самі по собі не доводять запуск MCP, компіляцію SQLcl або доступність цілі. Нативний пакет не завантажує залежності під час запуску MCP і не потребує вручну доданого глобального MCP-сервера.

Адміністратор керованого робочого простору може обмежувати доступність плагінів. Наведені CLI-команди виконують локальну нативну реєстрацію, а не розгортання для всієї організації. Якщо хост не надає інструментів, див. [усунення несправностей](troubleshooting.uk.md).

### Кероване встановлення середовища виконання

Керований інсталятор — альтернатива для перевіреного встановлення Node, Java, SQLcl і Playwright у каталозі користувача. З перевіреної копії репозиторію з Node 24:

```sh
git clone https://github.com/apexrest-dev/apexrest-codex.git
cd apexrest-codex
npm ci --ignore-scripts
npm run build
npm run site:build
npm run release:dry-run
```

Відкрийте `dist/releases/install-local.txt`: він містить точну команду Bash або PowerShell із назвою створеного архіву та SHA-256. Перегляньте її перед запуском. `--yes` дозволяє технічне налаштування; `--accept-oracle-license` є окремою згодою з наведеними умовами постачальника. Інсталятор може повторно використовувати сумісні наявні середовища виконання та типово записує керовані залежності в `~/.apexrest`.

Підтримуються `--dry-run`, `--offline`, `--cache-dir`, `--home`, `--codex-home` і `--native-only`. Увімкнення Codex лише для проєкту на перевіреному хості заблоковане; доступний окремий профіль через `--codex-home`. Профіль оболонки не змінюється. Реєстрація використовує ту саму ідентичність плагіна: не залишайте конкурентних встановлень цієї ідентичності в різних marketplace і не додавайте дубль глобального MCP-сервера.

Локальне пакування створює непідписані бета-артефакти й звітує про готовність. Воно не публікує та не засвідчує стабільний випуск.

## Підключення й налаштування

Інтерактивно збережіть потрібні з’єднання в локальному сховищі SQLcl. За можливості використовуйте окремі з’єднання для читання й розгортання. Надайте Codex назви посилань на з’єднання та несекретну ідентичність цілі:

> Налаштуй тестове середовище APEXREST із локально збереженими з’єднаннями SQLcl `saved-read-connection` і `saved-deploy-connection`. Робочий простір — `YOUR_WORKSPACE`, parsing schema — `YOUR_SCHEMA`, ID застосунку — `100`, унікальна назва бази даних — `YOUR_DB`, сервіс — `YOUR_SERVICE`, URL застосунку — `https://your-host.example/ords/r/workspace/app/`. Перевір, що з’єднання для читання відповідає цій ідентичності.

Замініть кожен заповнювач справжнім значенням цілі. APEXREST зберігає назви, а не паролі. Ініціалізація проєкту не вигадує цільового середовища. Точну схему середовища, приватну політику довіри й дозволені origins тестів описано в [конфігурації](configuration.uk.md).

## Створення або перенесення проєкту

Для нового застосунку використовуйте новий каталог і відповідний шаблон:

> Скористайся APEXREST, щоб створити порожній застосунок у новому проєкті `sales-app`. Налаштуй визначену тестову ціль, додай дашборд із реальними показниками джерела, потім заверши планування, дозволений імпорт і браузерні перевірки.

Для наявного застосунку:

> Скористайся APEXREST, щоб ініціалізувати проєкт existing-app у новому каталозі `sales-app` і перенести визначений тестовий застосунок. Збережи всі Oracle ID, метадані `.apex`, сторонні сторінки, спільні компоненти й автентифікацію. Додай запитаний дашборд, імпортуй його в той самий застосунок і перевір результат.

Перенесення й експорт використовують нові локальні каталоги та завершуються помилкою, якщо перезаписали б локальні зміни. Зберігайте згенеровані метадані Oracle під контролем версій. Для наступних змін використовуйте наявний робочий код; не переносьте застосунок заново щоразу. Див. [наявні застосунки](existing-app.uk.md).

## Редагування, планування, імпорт і перевірка

Плагін один раз оглядає проєкт і конфігурацію цілі, повторно використовує обмежені довідкові матеріали відповідної версії та групує пов’язані зміни коду. Планування включає реальну валідацію компілятором, тому окрема ідентична компіляція безпосередньо перед ним зазвичай зайва.

Перегляньте ціль і обсяг конкретного плану. Він прив’язує код, інструментарій, поточну ціль та історію і діє 30 хвилин. Явний запит створити, оновити чи імпортувати визначений застосунок розробки/тестування дозволяє необхідний імпорт у цих межах. Codex записує наявний дозвіл для точного плану й продовжує без повторного запиту того самого дозволу. Сторонні записи в схему, зміни автентифікації, інші цілі та production не входять у цей обсяг.

Apply перевіряє свіжу ідентичність і розбіжності, створює перевірену SQL-копію наявного застосунку, фіксує незмінний код і використовує стійку координацію. Тривалі операції MCP повертають ID завдання; відстежуйте його до завершення замість повторного запуску операції. Невдалий або невідомий результат запису потребує діагностики чи звіряння перед повторенням.

Для сторінки чи дашборда звірте відповідні вихідні запити лише для читання та огляньте імпортовану поведінку у вбудованому браузері Codex, якщо він доступний. Дочекайтеся завершення завантаження асинхронних регіонів APEX, потім перевірте змінені фільтри, діаграми, дати й порожні стани. Запустіть налаштовані автоматизовані набори, відповідні зміні. Записуйте ручні браузерні спостереження окремо; порожній список наборів не означає успіх автоматизованих тестів. Див. [тестування](testing.uk.md).

## Використання CLI

Нативне встановлення надає плагін Codex, але не додає команду `apexrest` до `PATH` оболонки. У перевіреній копії репозиторію можна запускати CLI безпосередньо через Node 24:

```sh
node plugins/apexrest-apex/runtime/apexrest.mjs doctor --json
node plugins/apexrest-apex/runtime/apexrest.mjs project init ./crm --template customer-crm
```

Кероване встановлення створює `~/.apexrest/bin/apexrest` на macOS/Linux або `apexrest.ps1` у керованому каталозі `bin` на Windows. Якщо вибрано інший home, використовуйте відповідний шлях `<home>/bin`. У прикладах цей засіб запуску скорочено до `apexrest`; замініть його повним шляхом або командою Node з репозиторію:

```sh
apexrest connection add dev-read --sqlcl-name saved-read-connection
apexrest connection add dev-deploy --sqlcl-name saved-deploy-connection
apexrest project inspect --project ./crm --json
apexrest deploy plan --project ./crm --env dev --out plans/dev.json
apexrest deploy apply --project ./crm --plan plans/dev.json
```

Перед операціями з ціллю налаштуйте `environments.dev`, перегляньте проєкт і надайте йому довіру, а також дозволену політику для точної цілі. Шаблон CRM містить зміни схеми й обов’язкові SQL/E2E набори, тому його імпорт потребує відповідних дозволів і залежностей. Для суто діагностичного запуску компілятора використовуйте `apexrest apex validate --project ./crm --json`.

Довідка команд доступна через `--help`. CLI `apex export` використовує `--output`, а `deploy plan` — `--out`. JSON-вивід містить класифіковані результати й коди завершення. CLI та MCP використовують те саме ядро перевірок.

Викликаючи MCP-інструменти рівня проєкту, передавайте абсолютний каталог проєкту застосунку в аргументі `project`. Нативний сервер запускається в каталозі встановленого плагіна, тому відсутні чи відносні шляхи проєкту відхиляються до початку роботи. CLI-приклади визначають `--project` від робочого каталогу термінала.

## Видалення плагіна з репозиторію

Для прямого встановлення з репозиторію:

```sh
codex plugin remove apexrest-apex@apexrest
codex plugin marketplace remove apexrest
```

Видаляйте marketplace лише коли його записи більше не потрібні. Після видалення почніть нову задачу Codex. Це скасовує реєстрацію нативного плагіна; воно не є запитом видалити проєкти застосунків, резервні копії, облікові дані SQLcl або стійку історію розгортань. Кероване встановлення має власну команду `apexrest plugin uninstall` із перевірками належності.
