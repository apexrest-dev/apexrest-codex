# Команда розробки за явним вибором

[English](team.md) | Українська

За замовчуванням працює один агент. Команда запускається лише після явного вибору користувачем **Agent team** у **Settings → Defaults for new work** і збереження (`multiAgentEnabled: true`). Параметр запуску не може увімкнути команду. Браузер перевірки (`codex` або `external`) обирається там само. Дивіться [налаштування режимів](work-modes.uk.md). Опис незалежних review/QA нижче стосується лише увімкненого командного режиму; скріншоти від 17 вересня показують попередню версію панелі.

Нові запити реалізації використовують [роботу з APEX із чату](chat-workflow.uk.md). Single працює безпосередньо в наявному чаті Codex без іншого агента, запуску App Server, автовідкриття панелі, маршрутизації моделей чи очікування команди. Відповідь `current_session` і сумісний `teamId` фіксують запит; вони не засвідчують завершеної роботи. Поточний хост керує моделлю, дозволами й sandbox. Процес та керування нижче стосуються явно увімкнених команд: Codex відкриває їхню панель і повертає результат у початкову розмову. [Маршрутизація Auto](chat-workflow.uk.md#моделі-auto) обирає підтримувані моделі й рівні для кожного запланованого командного кроку.

Повний покроковий опис зі справжніми скріншотами: [агентний процес від завдання до перевіреного результату](agent-workflow.uk.md).

Основний вхід із чату — `$apexrest-work`; `$apexrest-team` надає пряме керування. Після увімкнення multi-agent у Settings runtime створює одного менеджера проєкту, від одного до трьох розробників і незалежного QA в окремих сесіях Codex App Server. Розробники працюють послідовно в одному проєкті. Менеджер визначає завдання; контролер створює ролі та забезпечує порядок їхньої роботи.

## Обов’язкова послідовність

Планування → розробка → рев’ю коду менеджером → незалежна QA-перевірка → рев’ю QA менеджером → завершення.

Відхилене рев’ю коду повертає процес до розробки. Після коректного звіту QA менеджер переглядає його навіть за невдалої перевірки. Схвалення менеджера не може скасувати невдалі чи недоступні QA-перевірки. Після виправлень рев’ю повторюються; дозволено щонайбільше три ревізії. Некоректні звіти, непідтримуваний протокол, відсутня інтерактивна відповідь і зміни файлів під час рев’ю лише для читання блокують успіх. Рішення прив’язані до дайджесту файлів проєкту; подальші зміни переводять результат у `review_stale`.

Дайджест включає невідстежувані файли та конфігурацію, крім `.git`, `.apexrest`, `node_modules` і `.DS_Store`. Для symlink враховується текст посилання, а не вміст зовнішньої цілі. Ці виключення та зовнішні залежності не охоплені гарантією дайджесту. Результат команди не є зовнішнім підписом або дозволом на production deploy; агенти використовують спільні машину та проєкт користувача.

## API та використання

| MCP-інструмент | CLI | Призначення |
| --- | --- | --- |
| `apexrest_team_start` | `team start` | Визначити збережений режим: запис поточної сесії для single або ID запуску для увімкненої команди |
| `apexrest_team_status` | `team status` | Прочитати фазу, ролі, повідомлення, рішення рев’ю й результат |
| `apexrest_team_message` | `team message` | Поставити уточнення користувача в чергу; анулювати завершення за попереднім запитом |
| `apexrest_team_cancel` | `team cancel` | Запросити переривання; не заявляти відкат |

```sh
apexrest team start --project /absolute/project --task "Add the requested APEX page" --execution-mode team --developers 2 --json
apexrest team status TEAM_ID --project /absolute/project --json
apexrest team message TEAM_ID "Also verify empty results" --project /absolute/project --json
apexrest team cancel TEAM_ID --project /absolute/project --json
```

Ці команди передбачають, що користувач уже увімкнув командний режим у Settings. Параметр запуску не може його увімкнути. Командні status/message/cancel не керують поточним чатом Codex і не зупиняють його.

Налаштований проєкт уже має бути довіреним. Виконуваний файл Codex і вхід мають працювати. Типовий sandbox розробника — `workspace-write`; `--sandbox read-only` підтримує роботу лише з аналізом. Типовий ліміт часу — 900 секунд, доступний діапазон від 30 до 3600. Моделі й рівень міркування обираються в режимі Auto, описаному нижче; ручного перемикача моделі немає. Фонова робота використовує звичайні ліміти Codex облікового запису.

## Спільні докази та межі

Кожна роль отримує обмежені командою інструменти `team_context` і `team_message`. Повідомлення надходять у наступний запланований хід або уточнюють активний. Вони не можуть адресувати сторонню сесію чи створити додаткових агентів. Контекст містить звіти колег, фактичні спостереження протоколу, рішення рев’ю та звіти QA. Стислі результати команд і доставка повідомлень зберігаються локально з редагуванням чутливих даних та обмеженнями розміру. Це доступні для перевірки докази виконання, а не гарантія правдивості кожного твердження про тести.

Приватні звіти зберігаються у `.apexrest/teams/<id>/`. Відповіді статусу обмежені; `fullReport` вказує на повний локальний звіт. Повідомлення можуть залишитися недоставленими, якщо адресат більше не матиме ходу. Прострочений heartbeat дає `outcome_unknown`; автоматичного повторного запуску немає. Лише одна команда володіє блокуванням проєкту. Скасування зупиняє подальшу роботу без відкату вже зроблених змін файлів чи бази.

Сесії менеджера та QA використовують sandbox і MCP-інструменти APEXREST лише для читання. Перевірки, що потребують недоступного запису, автентифікації чи додаткових дозволів, можуть заблокувати QA; контролер не може мовчки пропустити їх. Наявні сторонні інструменти підпорядковуються політиці Codex; файловий sandbox лише для читання не є універсальною межею дозволів віддалених сервісів. Авторизовані імпорти APEX зберігають перевірки цілі, backup, plan і дозволу deploy.

Плагін володіє цими тимчасовими сесіями та читає їхні рідні події завершення. Їхні ходи не публікуються у приватному реєстрі субагентів desktop-завдання. [Аудит коду Codex](codex-integration.uk.md) описує підтримувані точки розширення та точні межі гарантій.

## Перевірка

Протокольні fixtures у `tests/unit/team.test.ts` перевіряють порядок, відхилення, невдалу QA, некоректний результат, ізоляцію, зміни джерел, уточнення користувача, скасування та конкуренцію за блокування. Це не докази справжнього Codex чи Oracle. `scripts/verify-team-native.mjs` окремо запускає справжні сесії Codex на ізольованому локальному завданні з кодом і незалежно повторює тести. [Нативний звіт](evidence/team-native-local.json) фіксує спостережений результат. Жоден fixture не підтверджує імпорт Oracle чи відображення desktop-панелі.

Імена агентів закріплені: Mewtwo (менеджер), Pikachu/Charmander/Bulbasaur (розробники), Squirtle (QA). [Панель](panel.uk.md) показує локальні іконки, фактичну конфігурацію та поточні дії. Сталі ключі ролей зберігають повноваження рев’ю й адресацію; тимчасові сесії Codex не можна перейменувати через метадані.
