# Робота з APEX із чату Codex та автоматичний вибір моделей

Українська | [English](chat-workflow.md)

За замовчуванням працює один агент. Команда запускається лише після явного вибору користувачем **Agent team** у **Settings → Defaults for new work** і збереження (`multiAgentEnabled: true`). Параметр запуску не може увімкнути команду. Браузер перевірки (`codex` або `external`) обирається там само. Дивіться [налаштування режимів](work-modes.uk.md). Опис незалежних review/QA нижче стосується лише увімкненого командного режиму; скріншоти від 17 вересня показують попередню версію панелі.

Опишіть зміну Oracle APEX у поточному чаті Codex. [Скіл роботи з чату](../plugins/apexrest-apex/skills/apexrest-work/SKILL.md) визначає налаштований режим. У single робота виконується безпосередньо в цій наявній сесії. Увімкнений командний режим запускає окремі сесії ролей і відкриває їхню живу панель. Створювати завдання у вебінтерфейсі не потрібно.

## Single у поточному чаті

1. Codex визначає проєкт застосунку й зберігає запит, обмеження та дозвіл користувача.
2. `apexrest_work_start` повертає `executionHost: current_session` і `status: current_session`. Новий UUID `requestId` ідентифікує запит; точний повтор використовує той самий запис, а змінені вхідні дані з цим UUID відхиляються. Сумісне поле `teamId` — ідентифікатор запису запиту, а не фонового запуску чи результату завершення.
3. Поточна сесія читає лише доречні джерела/довідку, вносить зміни та виконує відповідні перевірки. Окремий агент, запуск App Server, пошук/маршрутизація моделей, додатковий крок планування, автовідкриття панелі чи `apexrest_team_wait` не потрібні. Незалежні читання об’єднуються; контекст і перевірки не повторюються без нової причини.
4. Для видимих змін APEX використовуйте `apexrest_browser_open` для налаштованого середовища й дотримуйтеся збереженого або явно обраного браузера. Відкриття URL не засвідчує перевірку. Чинні дозволи на імпорт, перевірка цілі, резервна копія, контроль дрейфу та захист розгортання залишаються обов’язковими.
5. Повідомте фактичні зміни, перевірки й обмеження в тій самій розмові. Виконанням керують модель, політика дозволів і sandbox хоста. Плагін окремо не обліковує цей чат, не забезпечує timeout завдання й не видає результат завершення, прив’язаний до дайджесту. Уточнення та скасування користувача відбуваються в поточній розмові Codex.

## Командний процес у чаті

За явно увімкненого командного режиму `apexrest_work_start` створює внутрішній запуск і приватний URL панелі. Хост відкриває її всередині Codex, потім використовує `apexrest_team_wait` для змістовного прогресу чи кінцевого результату. Відповідь `unchanged: true` залишається короткою; `apexrest_team_status` надає обмежені звіти. Codex передає уточнення наявній команді й повертає її два рев’ю менеджера, незалежний QA та обмеження в той самий чат. Лише `completed` з актуальним дайджестом джерел означає перевірене завершення команди; це не дозвіл на розгортання.

Помилка панелі зберігає ID команди та можливість спостереження. Не запускайте заміну через помилку відображення. Після переривання хостового кроку можна продовжити за наявним ID команди. Codex CLI може показати панель в інтерактивному терміналі або повідомляти прогрес у поточній розмові, коли окремої термінальної поверхні немає. Порядок рев’ю, прив’язка до джерел, sandbox і довіра залишаються визначеними [командним процесом](team.uk.md).

Плагін не має глобального перехоплювача чату чи callback у довільні розмови. Нативне виявлення скілів обирає сценарій; після встановлення чи оновлення плагіна потрібне нове завдання Codex для оновлення кешованого каталогу скілів та інструментів. Окремі довідкові запити, налаштування й діагностика підключень використовують індивідуальні інструменти.

## Моделі Auto

Auto застосовується лише до окремих командних сесій. Single використовує модель, уже обрану в поточному чаті Codex. Для команд Auto отримує поточні моделі облікового запису та підтримувані рівні міркування через Codex App Server `model/list`. Для кожного `turn/start` задаються модель і підтримуваний рівень, зі збереженням окремих сесій ролей. Крок планування менеджера повертає структуровану оцінку складності, тому класифікація не додає виклику моделі. Самі лише заборони виходу за межі завдання не означають складну роботу.

| Робота | Бажаний вибір |
| --- | --- |
| Початковий план менеджера | GPT-5.6 Sol, medium |
| Просте завдання розробника | GPT-5.6 Luna, low |
| Звичайна реалізація, рев’ю менеджера та QA | GPT-5.6 Sol, medium |
| Складна реалізація й рев’ю менеджера | GPT-6 Astra, high; QA починає із Sol, medium |
| Перше виправлення реалізації | Щонайменше balanced/medium |
| Два невдалі цикли реалізації | Strong/high для наступних запланованих кроків у межах чинного ліміту трьох ревізій |

Причини доопрацювання відрізняють дефекти реалізації від відсутніх налаштувань, дозволів чи доказів. Заблоковані передумови не підвищують модель. Нова вимога користувача скидає попередню оцінку простого завдання. Класифікація й підвищення впливають лише на вибір моделі; вони не надають доступ і не обходять невдалий QA.

Можна обрати лише модель із поточного каталогу. Відомі альтернативи включають Terra та GPT-5.5; останній резервний варіант — доступна типова модель каталогу. Непідтримуваний рівень міркування замінюється підтримуваним low/medium/high або minimal/none із записаним поясненням. Auto ніколи не обирає extra-high/max/ultra. Порожній, непідтримуваний чи некоректний каталог блокує запуск замість мовчазного успадкування дорогої моделі.

Панель і CLI показують обрану модель, рівень, причину вибору, накопичувані токени, доступний поділ input/cache/output/reasoning і загальний ліміт часу. Кешований input є частиною input; reasoning output є частиною output. Не додавайте ці підмножини повторно й не сприймайте токени як рахунок. Повідомлене Codex перенаправлення моделі оновлює фактичну модель у панелі та історію подій. Завдання має ліміт часу, а не жорстку межу витрат токенів.

## Контекст і докази

Кожна командна роль отримує обмежений список учасників, доречні повідомлення колег та недавні підсумки рев’ю й QA. Сирі журнали команд зберігаються у приватному звіті замість копіювання в кожен крок. Скорочені підсумки посилаються на повний звіт; незалежне читання джерел і фактичні перевірки залишаються обов’язковими. Це зменшує повторний контекст, але не встановлює відсоток економії між різними завданнями чи використанням підписки Codex.

[Документація App Server](https://learn.chatgpt.com/docs/app-server) описує виявлення моделей, перевизначення моделі й рівня на кроці та повідомлення про токени. Локальні fixture-тести охоплюють маршрутизацію, резервний вибір, обов’язкові рев’ю, повтор запуску та очікування. Справжнє виконання моделей Codex, відображення браузера й перевірки Oracle — окремі рівні доказів; див. [стан реалізації](implementation-status.uk.md).
