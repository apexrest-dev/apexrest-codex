# Робота з APEX із чату Codex та автоматичний вибір моделей

Українська | [English](chat-workflow.md)

За замовчуванням працює один агент. Команда запускається лише після явного вибору користувачем **Agent team** у **Settings → Defaults for new work** і збереження (`multiAgentEnabled: true`). Параметр запуску не може увімкнути команду. Браузер перевірки (`codex` або `external`) обирається там само. Дивіться [налаштування режимів](work-modes.uk.md). Опис незалежних review/QA нижче стосується лише увімкненого командного режиму; скріншоти від 17 вересня показують попередню версію панелі.

Опишіть зміну Oracle APEX у поточному чаті Codex. Автоматично доступний [скіл роботи з чату](../plugins/apexrest-apex/skills/apexrest-work/SKILL.md) запускає обраний режим одного агента чи команди, відкриває її живу панель у вбудованому браузері Codex і повертає кінцевий результат у той самий чат. Користувачеві не потрібно створювати завдання у вебінтерфейсі. Панель залишається доступною для спостереження й необов’язкових уточнень.

## Життєвий цикл у чаті

1. Codex визначає налаштований проєкт застосунку й зберігає повний запит, обмеження та дозвіл користувача.
2. `apexrest_work_start` створює внутрішній запуск за збереженими параметрами та готує приватний URL панелі, який обирає цю команду й розділ Agent team. Кожне завдання має новий UUID `requestId`. Точний повтор запиту повертає ту саму команду; використання UUID з іншими параметрами відхиляється.
3. Хост відкриває URL інструментом вбудованого браузера Codex. Codex CLI може показати панель в інтерактивному терміналі або повідомляти перебіг у поточній розмові, коли окремої термінальної поверхні немає. Зовнішній браузер чи новий користувацький чат не потрібні.
4. `apexrest_team_wait` очікує до 30 секунд змістовної зміни або кінцевого стану. Його курсор ігнорує оновлення лише heartbeat чи токенів. Відповідь `unchanged: true` містить лише короткий стан; повні обмежені звіти доступні через `apexrest_team_status` і при зміненому чи кінцевому результаті очікування. Хост продовжує виконання запиту, повідомляє важливий прогрес і передає уточнення наявній команді.
5. Той самий чат отримує фактичний кінцевий результат: зміни, власні перевірки єдиного агента або два рев’ю менеджера й незалежний QA команди, а також обмеження. Лише `completed` з актуальним digest джерел означає перевірене завершення. Успіх команди не є дозволом на розгортання.

Помилка панелі зберігає ідентифікатор команди та можливість спостереження. Не запускайте заміну через помилку відображення. Після переривання хостового кроку можна продовжити за наявним ідентифікатором команди. Плагін не має глобального перехоплювача чату чи callback у довільні desktop-розмови: нативне виявлення скілів обирає сценарій, а початковий хостовий крок відкриває панель і повідомляє результат. Після встановлення чи оновлення плагіна потрібне нове завдання Codex для оновлення кешованого каталогу скілів та інструментів.

Окремі довідкові запити, налаштування й діагностика підключень використовують індивідуальні інструменти без команди розробки. Порядок рев’ю, прив’язка до джерел, sandbox, довіра й захист розгортання відповідають [обов’язковому командному процесу](team.uk.md).

## Моделі Auto

Auto — єдиний режим вибору моделі. Він отримує поточні моделі облікового запису та підтримувані рівні міркування через Codex App Server `model/list`. Для кожного `turn/start` задаються модель і підтримуваний рівень, зі збереженням окремих сесій ролей. Крок планування менеджера або єдиного агента повертає структуровану оцінку складності, тому класифікація не додає виклику моделі. Самі лише заборони виходу за межі завдання не означають складну роботу.

| Робота | Бажаний вибір |
| --- | --- |
| Початковий план менеджера | GPT-5.6 Sol, medium |
| Просте завдання розробника | GPT-5.6 Luna, low |
| Звичайна реалізація, рев’ю менеджера та QA | GPT-5.6 Sol, medium |
| Складна реалізація й рев’ю менеджера | GPT-6 Astra, high; QA починає із Sol, medium |
| Перше виправлення реалізації | Щонайменше balanced/medium |
| Два невдалі цикли реалізації | Strong/high для наступних запланованих кроків у межах чинного ліміту трьох ревізій |

Причини доопрацювання відрізняють дефекти реалізації від відсутніх налаштувань, дозволів чи доказів. Заблоковані передумови не підвищують модель. Нова вимога користувача скидає попередню оцінку простого завдання. Класифікація й підвищення впливають лише на вибір моделі; вони не надають доступ і не обходять невдалий QA.

Можна обрати лише модель із поточного каталогу. Відомі альтернативи включають Terra та GPT-5.5; останній резервний варіант — доступна типова модель каталогу. Непідтримуваний рівень міркування замінюється підтримуваним low/medium/high або minimal/none із записаним поясненням. Auto ніколи не обирає extra-high/max/ultra. Порожній, непідтримуваний чи некоректний каталог блокує запуск замість мовчазного успадкування дорогої моделі.

Панель і CLI показують обрану модель, рівень, причину вибору, накопичувані токени, доступний поділ input/cache/output/reasoning і загальний ліміт часу. Кешований input є частиною input; reasoning output є частиною output. Не додавайте ці підмножини повторно й не сприймайте токени як рахунок. Повідомлене Codex перенаправлення моделі оновлює фактичну модель у панелі та історію подій. Завдання має ліміт часу, а не жорстку межу витрат токенів.

## Контекст і докази

Кожна роль отримує обмежений список учасників, доречні повідомлення колег та недавні підсумки рев’ю й QA. Сирі журнали команд зберігаються у приватному звіті замість копіювання в кожен крок. Скорочені підсумки посилаються на повний звіт; незалежне читання джерел і фактичні перевірки залишаються обов’язковими. Це зменшує повторний контекст, але не встановлює відсоток економії між різними завданнями чи використанням підписки Codex.

[Документація App Server](https://learn.chatgpt.com/docs/app-server) описує виявлення моделей, перевизначення моделі й рівня на кроці та повідомлення про токени. Локальні fixture-тести охоплюють маршрутизацію, резервний вибір, обов’язкові рев’ю, повтор запуску та очікування. Справжнє виконання моделей Codex, відображення браузера й перевірки Oracle — окремі рівні доказів; див. [стан реалізації](implementation-status.uk.md).
