# Next actions and exact dependencies

English | [Українська](next-actions.uk.md)

APEXlang retrieval optimization is implemented and locally checked; see [its measured scope](apexlang-optimization.md). The next quality step is a broader fixed set of Codex authoring tasks with compiler attempts, elapsed time and context usage recorded, followed by authorized connected/browser checks. The twelve retrieval cases and three compiled compositions do not replace these task-level evaluations. Codex is the sole product target; portable-package release work is retired.

The repository provides English and Ukrainian documentation, accessible architecture/deployment diagrams in both languages, direct GitHub marketplace installation, a self-contained native bundle, integrity gates and cross-platform CI. [Getting started](getting-started.md) covers installation. [Implementation status](implementation-status.md), [local checks](evidence/local-checks.json) and [native installation evidence](evidence/native-repository.json) state the actual scope and source digest of each verification run.

Keep both documentation languages synchronized for future changes and run `npm run docs:check`, the site build and packaging checks. Documentation checks and site browser observations do not refresh Oracle or native-host evidence.

The installable beta retains these stable release dependencies:

1. **Configure a dedicated connected integration environment.** Identify a disposable application and explicit database/workspace/schema identity, supply named local SQLcl connections, and obtain authorization for the particular mutations the fixture requires. Configure authenticated browser access and utPLSQL only for applicable SQL suites. APEXREST service tables are not deployment prerequisites; local control remains the default.
2. **Complete the connected fixture matrix.** Verify export/adopt, no-op and changed-component import/export round trips, metadata/shared-component preservation, unsupported-component rejection, SQL backup and restore, migration checksums, runner contention, disconnect/cancellation and unknown-outcome reconciliation. Add authenticated CRUD, negative validation and run-specific cleanup. The happy-path integration harness alone does not certify these failure cases.
3. **Verify each native client platform.** Run clean-machine Codex installation and bootstrap on Linux x64, Windows x64 and WSL2, and refresh the macOS lifecycle for the release source. Cover missing dependencies, license refusal, proxy/CA, browser OS dependencies, cache miss/corruption, interrupted/concurrent setup, upgrades and uninstall preservation. Hosted fixture/packaging CI does not replace native-host tests. Project-only enablement needs a supported, verified Codex mechanism.
4. **Complete protection and recovery evidence.** Exercise unrelated-plugin preservation, cross-version cache refresh/rollback, partial install recovery and process-tree termination. Validate externally signed production approval on a protected runner inaccessible to project or agent code. Browser payload verification currently relies on pinned Playwright. Redaction does not establish exhaustive sensitive-data detection.
5. **Prepare an authorized immutable release.** Gather all required evidence against the exact release source digest, configure protected CI and external signing/publication credentials, and verify support channels and any optional npm ownership. Enable publishing only for the authorized release, rebuild artifacts and pass readiness before publication. The beta is currently unsigned and the publisher is disabled.
6. **Optional sandbox.** Implement and verify a legitimate pinned Linux Oracle Free/APEX/ORDS/utPLSQL stack with approved provisioning, private credentials and persistent volumes. Keep `supported:false` until it works; ordinary shutdown must preserve data.

For future visible changes, follow the [in-app browser rule](../plugins/apexrest-apex/skills/apexrest-test/SKILL.md#in-app-browser-verification). Check affected behavior after loading completes and keep observations separate from automated results. An identified development/test application request includes its necessary scoped import; production still requires protected external approval.

Implementation, local fixtures, native-host checks and connected integration remain separate. Missing or stale evidence cannot become a passing release gate through a documentation update.
