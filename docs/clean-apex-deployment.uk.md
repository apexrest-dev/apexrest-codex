# Розгортання без службових таблиць

[English](clean-apex-deployment.md) | Українська

2026-09-12 користувач змінив правила плагіна: відсутність службових таблиць APEXREST не має блокувати звичайне розгортання на чистій підтримуваній інсталяції APEX. Початкова специфікація збережена; поправку записано в AGENTS.md та ADR 007.

## Реалізовано

- Якщо `deploymentControl` не задано, plan і apply вибирають `local`. Запитів до таблиць APEXREST чи DDL налаштування в цьому режимі немає.
- Локальна історія міграцій записує контрольні суми й `started` до виконання SQL. Успішні міграції не повторюються; змінені суми й невирішена історія зупиняють наступний план.
- Локальне володіння забезпечує послідовність застосунків зі спільними БД/сервісом/parsing schema в одному керованому home. Після завершення власника підготовки можливе відновлення; володіння записом після невідомого результату потребує звіряння.
- План прив’язує backend координації, обсяг та ідентичність локального сховища. Перевірки розбіжностей коду/цілі, дозволів, копій, обов’язкових тестів і політика відновлення зберігаються.
- `deploymentControl: "database"` залишається необов’язковим для явно налаштованої координації через таблиці. Якщо вибраний backend не працює, непомітного переходу до порожньої локальної історії немає.
- Навички deploy, database і setup вказують Codex продовжувати звичайне розгортання без запиту службових таблиць. utPLSQL є залежністю SQL-наборів, а не розгортання лише застосунку.

Локальний стан належить `$APEXREST_HOME/deployment-control/` і має зберігатися між запусками. Різні машини/home не мають спільного блокування чи історії: використовуйте стійкий CI runner із зовнішнім послідовним виконанням або явно налаштовану координацію БД. Переходячи з необов’язкового database backend, збережіть і звірте його історію; нове порожнє локальне сховище не є безпечною стратегією міграції.

## Обсяг перевірки

Локальні тести покривають plan/apply без звернень до службових таблиць, збереження історії міграцій, відхилення контрольних сум, збереження перерваного запису, конкуренцію за схему, окремий Node runner, завершеного власника й відхилення зміни сховища. Записи Oracle тут явно є фікстурами, а не доказами розгортання з підключенням. Див. [тестування](testing.uk.md) і [стан реалізації](implementation-status.uk.md) щодо записаних перевірок та відкритих умов випуску.

Імпорти з підключенням, відновлення, ін’єкція збоїв міграцій, автоматизовані SQL/CRUD набори й конкуренція незалежних машин потребують власних інтеграційних доказів. Звіти нативного життєвого циклу, setup і компілятора шаблонів зберігають початкові digest коду та обсяг перевірки. Готовність стабільного випуску залишається false.
