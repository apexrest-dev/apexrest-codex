# Програмна автоматизація для Codex

[English](codex-automation.md) | Українська

Плагін призначений для Codex desktop і Codex CLI. [24 обробники MCP](../packages/core/src/operations.ts) уже виконують звичайний програмний код; механічні кроки компіляції, читання метаданих і розгортання не потребують моделі. Codex забезпечує розуміння завдання й зміни коду. Явно ввімкнені команди додатково використовують сесії Codex App Server для реалізації та незалежного рев’ю.

## Що працює без ШІ

У назвах нижче пропущено MCP-префікс `apexrest_`. Програмне виконання також потребує відповідного дозволу на зміни.

| Інструменти | Програмна відповідальність | Внесок Codex |
| --- | --- | --- |
| `doctor`, `project_inspect` | Перевірити можливості й конфігурацію проєкту; за потреби обчислити хеші джерел | Пояснити відсутні передумови й вибрати потрібний контекст |
| `metadata_read` | Перевірити межі й ціль, виконати дозволені запити з пагінацією | Вибрати об’єкти й зрозуміти їхній бізнес-зміст |
| `reference_search`, `reference_read` | Ранжувати, кешувати, ділити на сторінки й читати зафіксовану довідку | Вибрати відповідний синтаксис і рішення проєктування |
| `apex_generate`, `apex_export`, `apex_validate` | Виконати генерацію Oracle, експорт у staging і перевірку компілятором | Визначити застосунок і виправити джерела за діагностикою |
| `deploy_plan`, `deploy_apply` | Створити незмінний план; забезпечити ідентичність, дозволи, резервування, drift, lease і перевірку результату | Пояснити зміну й діяти в межах наданого користувачем дозволу |
| `test_run` | Виконати налаштовані набори перевірок і зібрати фактичні докази | Вибрати доречні перевірки, написати твердження й оцінити покриття |
| `job_status`, `job_cancel`, `artifact_read` | Очікувати, відстежувати скасування й читати обмежені очищені артефакти | Зрозуміти результат; з’ясувати невідомий результат перед повторенням запису |
| `browser_open` | Визначити налаштовані URL і передачу керування браузеру | Використати доступні засоби браузера Codex і оцінити видиму поведінку |
| `panel_open`, `panel_status`, `panel_action` | Надати локальний UI, зібрати стан і виконати перевірені дії | Вибрати дію для завдання; дія явно ввімкненої команди може запустити роботу моделі |
| `work_start`, `team_start`, `team_status`, `team_wait`, `team_message`, `team_cancel` | Спрямувати запити, зберегти записи й забезпечити переходи команди | Single працює в поточному чаті; ввімкнені команди використовують окремі сесії моделей |

Жоден обробник не потребує додаткової моделі лише для форматування звіту, опитування worker, переліку файлів чи пошуку точної довідки. Розуміння предметної області, проєктування застосунку, нетривіальні зміни й змістовне рев’ю все ще потребують міркування Codex. Успішні програмні перевірки не доводять відповідності застосунку потребам користувача.

## Реалізоване скорочення звернень до моделі

- Шість тривалих MCP-інструментів (`apex_generate`, `apex_export`, `apex_validate`, `deploy_plan`, `deploy_apply`, `test_run`) запускають завдання один раз і очікують у тому самому виклику. `waitSeconds` приймає 0–30, типове значення — 25. Після завершення повертається наявне завдання з вкладеним результатом, а фактичний результат також відображається у зовнішніх `ok`, `status`, `exitCode` і MCP `isError`; після timeout — той самий `jobId` для `job_status`. Значення 0 дає негайне підтвердження. Скасування очікування MCP не скасовує саме завдання; явне скасування завдання зберігає чинні запобіжники.
- `metadata_read` приймає наявний одиничний запит або `requests` із 1–8 запитів. Усі запити перевіряються до SQL; пакет один раз перевіряє ціль, потім послідовно виконує запити в дозволених межах. Кожен запит зберігає пагінацію й позначку недовіреного вмісту. Некоректний пакет не перетворюється на частковий успіх.
- Single `work_start` включає стислий контекст шляхів проєкту, конфігурації середовища й параметрів перевірки. `project_inspect` також приймає `detail: "summary"`; типова повна перевірка не змінена. Стислий варіант не читає джерел застосунку й не викликає Oracle. Налаштовані значення цілі не є перевіреною ідентичністю цілі.
- Обмежений MCP-вивід зберігає придатну для дій вкладену діагностику помилок, ідентифікатори артефактів і відомості про безпеку плану розгортання; повний очищений результат доступний через читання артефактів.

Реалізація міститься в [обробці завдань](../packages/mcp/src/job-tools.ts), [метаданих](../packages/core/src/metadata.ts), [контексті проєкту](../packages/core/src/project.ts) та [обробці виводу](../packages/mcp/src/output.ts). [Локальна валідація](evidence/codex-automation-local.json) для `0.3.0-beta.1+codex.20260921193125`: пройшли 217 unit-тестів, 22 контрактні та 14 тестів пакування (253 загалом), typecheck і lint.

[Перевірка зібраних CLI/stdio MCP](evidence/codex-automation-runtime.json) підтверджує 24 інструменти, шість із типовим очікуванням 25 секунд, повернення успіху й помилки одним викликом у кожному випадку з правильним зовнішнім результатом та single через `current_session`. Для 50 синтетичних файлів джерел стислий контекст становив 659 байтів UTF-8 проти 4,494 для повної перевірки (-85.34%). Це локальні розміри відповідей і кількість викликів; перевірки не вимірюють часу виконання Oracle й не доводять економії оплачуваних токенів. Ця runtime-перевірка не включала звернення до моделі, App Server, Oracle чи перевірку застосунку в браузері.

## Виконання для Codex

Використовуйте встановлений плагін Codex, його локальні інструменти stdio MCP і поточний чат для single. Завантажуйте лише потрібні частини навичок і довідки; використовуйте отримані підсумки й ідентифікатори завдань замість відтворення програмного стану в запитах. Відкривайте панель розробки за потреби. Оркестрацію App Server використовуйте лише для явно ввімкнених команд.

Не додаються непідтверджені API приєднання worker до поточного чату, керування браузером desktop чи розширення його бічної панелі. Передача URL браузеру відокремлена від фактичної браузерної перевірки. [Аудит коду](codex-integration.uk.md) документує спостереження конкретних версій хоста; підтримка метаданих сама собою не доводить нативного відображення UI. Шар сумісності з іншими хостами не додається.

Залишається порівняти однакові реальні завдання Codex за фактичними лічильниками хоста, потім виконати окремо дозволені перевірки Oracle і браузера застосунку. Локальні фікстури не доводять наскрізного прискорення нативної роботи, економії оплачуваних токенів чи правильності справжнього розгортання. У кожній оптимізації слід зберігати ідентичність цілі, явні межі дозволу на розгортання, резервні копії, перевірки drift, обробку невідомого результату й установлені обов’язкові набори тестів.
